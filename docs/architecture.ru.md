# Архитектура

Этот проект использует модульный многоуровневый дизайн с полным разделением между ядром движка сборки и точками входа платформы. CLI, BuildServer, DesktopApp и LinuxGateway разделяют одну и ту же основную логику — различия заключаются только в уровне входа и способе взаимодействия.

## Ответственность каталогов

Инструмент организован по следующим каталогам по ответственности:

- `Cli/`: Точка входа команд, парсинг аргументов командной строки, маппинг быстрых команд (`ShortcutCommands`).
- `ConsoleUi/`: Интерактивный UI консоли, включая мастер инициализации, редактор конфигурации и подсказки ввода.
- `Configuration/`: Модели конфигурации, чтение/запись файлов конфигурации, выбор файлов конфигурации, разрешение путей, примерные конфигурации. Поддерживает конфигурации платформ `ios`, `android` и `tiktok`.
- `Workflow/`: Оркестрация конвейера сборки, контекст выполнения, обновление конфигурации во время выполнения, снимки конфигурации.
- `Services/`: Кроссплатформенные общие бизнес-возможности, включая синхронизацию Git, проверку окружения, подготовку каталогов, валидацию Unity-проекта и валидацию безопасности путей.
- `Modules/Common/`: Общие возможности платформенных модулей, включая интерфейс платформенного Pipeline, построение аргументов команд Unity, диагностику логов Unity и чтение метаданных Unity.
- `Modules/Ios/`: Специфичные для iOS возможности сборки, включая экспорт Unity Xcode-проекта, локацию Xcode project/workspace, `xcodebuild archive/export`.
- `Modules/Android/`: Специфичные для Android возможности сборки, включая сборку APK/AAB Unity, загрузку через Google Play Publishing API; подкаталог `GooglePlay/` обрабатывает детали HTTP API, OAuth и Service Account.
- `Modules/Tiktok/`: Специфичные для TikTok Mini-Game возможности, включая конвейер сборки WebGL (`TiktokBuildPipeline`), сервис сборки (`TiktokBuildService`) и загрузку через API TikTok Open Platform (`TiktokUploadService`). Полностью независимо от iOS/Android — не влияет на существующие потоки.
- `Infrastructure/`: Общая инфраструктура, включая логирование (`BuildLogger`), выполнение процессов (`ProcessRunner`), инструменты путей (`PathTools`), периметры безопасности путей (`PathSafety`) и маскирование чувствительных данных. Эти возможности разделяются CLI, BuildServer и DesktopApp.
- `UnityBuildScripts/Ios/`: Скрипт сборки Unity Editor iOS для копирования в `Assets/Editor` Unity-проекта.
- `UnityBuildScripts/Android/`: Скрипт сборки Unity Editor Android для копирования в `Assets/Editor` Unity-проекта.
- `BuildServer/`: Веб-платформа сборки, включая API (`ApiRoutes`), встроенный фронтенд (`wwwroot/`), фоновый Worker (`BuildWorkerService`), вход MCP/Agent (`McpEndpoint`), API узла Gateway (`GatewayEndpoint`), email-уведомления (`EmailNotificationService`), управление хранилищем (`StorageCleanupService`), сканирование артефактов (`ArtifactScanner`), обслуживание (`MaintenanceService`), обратное подключение (`Reverse/`) и JSON-персистентность (`Persistence/`).
- `LinuxGateway/`: Многоустройский единый вход, включая API (`ApiRoutes`), встроенный фронтенд (`wwwroot/`), клиент узлового шлюза (`NodeGatewayClient`), обновление узлов (`NodeRefreshService`), обновление задач (`JobRefreshService`), управление обратным подключением (`Reverse/`), онлайн-самообновление (`SelfUpdateService`) и JSON-персистентность (`Persistence/`).
- `DesktopApp/`: Десктопный клиент Avalonia UI 11, включая Views (14 страниц), ViewModels (15 моделей представления), Services (`BuildRunner` / `ProfileStore` / `ServerSyncService`), Controls (кастомные контролы) и Styles (ресурсы стилей). Ссылается на главный проект через `InternalsVisibleTo` + `Compile Remove` для повторного использования всей основной логики.
- `deploy/`: Шаблоны продакшен-развёртывания, такие как macOS `launchd` plist и файлы Docker-развёртывания.

## Ключевые принципы проектирования

### Оркестрация конвейера отделена от платформенных возможностей

`AutomationWorkflow` только оркестрирует шаги — он не обрабатывает напрямую детали Git, Unity, Xcode, Google Play или TikTok. При добавлении платформенных возможностей они должны быть помещены в соответствующий каталог `Modules/<Platform>/` и вызваны workflow; кроссплатформенные возможности помещаются в `Services/`. В настоящее время поддерживаются три платформенных Pipeline:

- `IosBuildPipeline` — Git → Unity → Xcode archive/export → загрузка ASC
- `AndroidBuildPipeline` — Git → Unity → APK/AAB → загрузка Google Play
- `TiktokBuildPipeline` — Git → Unity → WebGL → загрузка TikTok Open Platform

### Редактор конфигурации на основе полей

Редактор конфигурации использует список дескрипторов полей для управления меню и логикой изменения. При добавлении полей конфигурации сначала добавьте запись в список полей `ConfigEditor`, избегая рассеивания отображения меню и логики изменения switch-case.

### Фундамент безопасности

При подключении к веб-бэкендам, Worker или MCP/Agent все точки входа должны повторно использовать уже реализованные в CLI возможности:

- `PathSafetyValidator`: Проверяет, что workspace, каталоги репозиториев, Unity-проекты, артефакты, логи, вывод Xcode и archive/export находятся в разрешённых корневых каталогах.
- `GitRepositoryPolicyValidator`: Проверяет формат Git URL и белый список `allowedRepositoryUrls`.
- `BuildConfigSnapshotWriter`: Генерирует `Logs/build-config-snapshot.json` при каждом реальном запуске, записывая снимок конфигурации, разрешённые пути и аргументы CLI.
- `SensitiveText`: Единообразно маскирует общие токены/пароли в логах, командах, stdout/stderr и снимках конфигурации.

Эти возможности не должны ограничиваться уровнем Web/API. Worker также должен вызывать их перед выполнением сборок, чтобы предотвратить обход точек входа и прямой запуск опасных конфигураций.

## Архитектура BuildServer

BuildServer — точка входа Web/Agent для CLI со следующим дизайном:

### Последовательная очередь

Дизайн с одной машиной, одним Worker и последовательной очередью — намеренный: Unity, Xcode, Gradle, сертификаты подписи и каталоги кэша обычно не переносят конкурентного взаимодействия на одной машине. Машинное масштабирование обрабатывается LinuxGateway.

### Слой сервисов

| Сервис | Файл | Ответственность |
|------|------|------|
| Очередь задач | `BuildQueueService.cs` | Управление enqueue, dequeue и переходами состояния задач сборки |
| Фоновый Worker | `BuildWorkerService.cs` | Последовательное потребление очереди, вызов CLI для сборок |
| Email-уведомления | `EmailNotificationService.cs` | Отправка email-уведомлений об успехе/провале после завершения сборок |
| Сканер артефактов | `ArtifactScanner.cs` | Сканирование каталогов артефактов задач, генерация списков артефактов |
| Читатель логов | `LogFileReader.cs` | Чтение и tail логов задач |
| Очистка хранилища | `StorageCleanupService.cs` | Ручная и автоматическая очистка исторических артефактов |
| Обслуживание | `MaintenanceService.cs` | Авто-очистка по RetentionDays/MaxArtifactBytes |
| Авто-локатор | `AutomationToolLocator.cs` | Поиск исполняемого файла CLI AutomationUnityBuildIOS |

### Обратное подключение

Каталог `BuildServer/Reverse/` реализует возможность BuildServer проактивно подключаться к LinuxGateway, позволяя узлам за NAT/интранетом планироваться LinuxGateway без публичного exposition.

## Архитектура LinuxGateway

LinuxGateway не запускает Unity, не хранит Unity-проекты и не содержит Apple-сертификатов. Он только:

1. Предоставляет веб-вход и управление устройствами.
2. Регистрирует узлы (прямое или обратное подключение).
3. Перенаправляет задачи в BuildServer каждого узла.
4. Проксирует логи и артефакты.

### Слой сервисов

| Сервис | Файл | Ответственность |
|------|------|------|
| Клиент узлового шлюза | `NodeGatewayClient.cs` | Вызывает endpoints `/api/gateway/*` BuildServer узла |
| Обновление узлов | `NodeRefreshService.cs` | Периодически обновляет статус узлов и синхронизацию проектов/конфигураций |
| Обновление задач | `JobRefreshService.cs` | Периодически обновляет статус, логи и артефакты удалённых задач |
| Онлайн-самообновление | `SelfUpdateService.cs` | Проверяет и скачивает пакеты обновлений из Gitee/GitHub Releases |

### Обратное подключение

Каталог `LinuxGateway/Reverse/` управляет генерацией Enrollment Token для подключений, инициируемых BuildServer, регистрацией узлов и поддержанием WebSocket-соединений.

### Онлайн-самообновление

`SelfUpdateService` поддерживает:
- Двухисточниковое обнаружение (параллельные запросы последней версии Gitee + GitHub).
- Скачивание пакетов обновлений tar.gz.
- Генерацию скрипта `apply-update.sh` для завершения резервного копирования + замены + перезапуска.
- .NET SDK на сервере не требуется — загружаются только предкомпилированные бинарники.

## Архитектура DesktopApp

DesktopApp использует Avalonia UI 11 + .NET 8 и повторно использует всю основную логику главного проекта через ссылку на проект:

- **InternalsVisibleTo** + **Compile Remove**: csproj главного проекта добавляет объявления, позволяя DesktopApp доступ к internal-членам, исключая файлы точек входа, такие как Program.cs.
- **ProfileStore**: Единообразно управляет персистентностью четырёх типов шаблонов конфигурации (проект/Unity/подпись/сертификат), хранящихся в каталоге `profiles/`.
- **ServerSyncService**: Подключается к BuildServer REST API через HttpClient для двусторонней синхронизации шаблонов и файлов конфигурации.
- **BuildRunner**: Обёртывает вызов CLI, предоставляя вывод логов в реальном времени и прогресс сборки.
- **AvaloniaUseCompiledBindingsByDefault=false**: Использует runtime-биндинги, избегая необходимости объявлять x:DataType в каждом файле .axaml.

Запустите `scripts/verify.ps1` для базовой регрессионной проверки: компиляция, точка входа help, dry-run, открытие-закрытие редактора конфигурации.
